# Note public links — design

Status: approved for implementation planning. Date: 2026-09-17.

## Goal

Let a note's owner/admin/editor generate an unauthenticated, read-only link
for one note. Anyone with the URL can view the note without logging in or
being a workspace member. This is new: the existing `ShareModal` "Internal
link" and member-grant flows both require Notted authentication.

## Scope (v1, deliberately minimal)

In scope:

- One public link per note (a toggle, not a list). Creating one while
  another exists replaces it (old URL stops working).
- Revoke, at any time, by the same role that could create one.
- Read-only note content only: no comments, no task list, no share/export
  controls, no editor chrome.
- Audit logging of create/revoke (not of anonymous views).

Explicitly out of scope for v1 (call out again if requested later):

- Per-link password or expiry.
- A workspace-wide "disable public links" admin policy.
- Multiple simultaneous links per note, or a link history/list.
- Comments or task-list content on the public page.
- View analytics / access logging beyond create/revoke audit events.
- Serving the link under a workspace's verified custom domain (Part 73).

## Data model

New table `note_public_links`
(`apps/api/src/database/schema/note-public-links.ts`):

| column | type | notes |
|---|---|---|
| `id` | uuid pk | |
| `note_id` | uuid, **unique** | one active link per note |
| `workspace_id` | uuid | denormalized for tenant scoping/query, matches existing convention |
| `token_hash` | varchar, **unique** | see Token below; never the raw token |
| `created_by_id` | uuid, FK → `users(id)` `ON DELETE SET NULL` | matches `workspace_domains.created_by_id` |
| `created_at` | timestamp, not null | |
| `updated_at` | timestamp, not null | present per project convention; in practice never updated — revoke deletes the row instead of flipping a flag |

Composite FK `(workspace_id, note_id) -> notes(workspace_id, id)`, same
cross-tenant-integrity pattern already used for `notes.project_id` /
`notes.folder_id` (see `notes.ts` module comment).

**Revoke deletes the row.** No `is_revoked` flag, no history. Re-enabling
always mints a fresh token via a fresh row.

Migration: next sequential Drizzle migration (currently `0024_...`, so this
lands as `0025_...`, name generated by `drizzle-kit generate`).

## Token

- 24 random bytes (192 bits), base64url-encoded — same entropy as API-key
  secrets (`api-key-secret.ts`).
- Stored as `token_hash`: `HMAC-SHA256(pepper, "notted:note-public-link:v1:" + raw)`,
  peppered with `BETTER_AUTH_SECRET`. Exact same deterministic-HMAC
  construction as `hashApiKey`, own domain-separation prefix so a collision
  between an API key and a public-link token is impossible even under a
  shared pepper.
- The raw token is returned **once**, in the create/regenerate response
  body, and never persisted or retrievable again — same "shown once"
  contract as API keys. This was a deliberate choice already implied by the
  `notes.ts` schema comment ("revocable hashed tokens"); the cost is that
  the owner must regenerate (invalidating the old link) if they lose a link
  they didn't copy. Acceptable for v1's minimal scope.
- The public URL carries **only the token**, no note or workspace ID:
  `https://<app>/p/:token`. Nothing about the URL shape is guessable or
  enumerable; the lookup is a single unique-index probe on the hash of the
  presented token.

## API

### Public, unauthenticated

`GET /api/v1/public/notes/:token`

- No auth guard. Rate-limited on the existing unauthenticated/strict
  per-IP tier (Part 5's guard) as defense-in-depth — the token's entropy
  already makes guessing infeasible, this just bounds scraping/abuse.
- Looks up `token_hash`, joins to `notes`. Returns 404 (not a distinguishing
  error) when: no matching token, the note is soft-deleted (`isDeleted`), or
  — automatically, via `ON DELETE CASCADE` on `workspace_id` — the
  workspace no longer exists.
- **Trash semantics**: the `note_public_links` row is untouched by
  trash/restore. A trashed note's link 404s; restoring the note makes the
  same link work again without the owner re-sharing anything.
- Response: `{ title, content: NoteDocument, pageSize, updatedAt }` — the
  read-only subset of `NoteDetail`. No capabilities, no IDs, no author
  identity beyond what's already in the document content itself.

### Management, authenticated

Under `workspaces/:workspaceId/notes/:noteId/public-link`
(`NotePublicLinkController`, mirroring `NoteSharesController`'s shape):

- **Authorization: `note.update`** for all three routes below — the same
  action `NoteSharesController`'s `managementAuthorization` and
  `NoteSharesService.authorizeManagement` already use, and the same action
  `NoteCapabilities.canShare` is literally defined as
  (`canShare: canUpdate` in `notes.service.ts`). This is a direct fit, not
  an approximation: `note.share`'s policy branch additionally validates a
  `delegation` (`targetUserId`, `requestedPermission`) against the actor's
  own delegation cap, which models "granting a specific member a specific
  permission" — a public link has no target member, so it does not belong
  under that branch. `note.update` is the correct, already-existing gate.
- `GET` — status only: `{ enabled: boolean, createdAt: string | null }`.
  Never re-returns the raw token.
- `PUT` — create or regenerate: deletes any existing row for the note,
  inserts a new one in the same transaction, returns `{ url: string }`
  once. Audit action `note.publicLink.created` (naming matches the existing
  `note.share.upserted` / `note.share.revoked` convention).
- `DELETE` — revoke: deletes the row if present; 200 no-op if none existed
  (matches idempotent-delete conventions elsewhere in the API). Audit action
  `note.publicLink.revoked`.
- Both mutations call `recordAudit` with `entityType: NOTE_AUDIT_ENTITY_TYPE`,
  `entityId: noteId`, the acting user, and the request ID — identical shape
  to `NoteSharesService.recordMutation`, no job-outbox domain event needed
  (nothing downstream currently reacts to note-sharing events besides
  notifications, and a public link has no target user to notify).

## Frontend

- New top-level route `apps/web/src/app/p/[token]/page.tsx` — a sibling of
  the `(auth)` and `(dashboard)` route groups, so it renders with **no**
  sidebar/header chrome (its own minimal layout).
- New unauthenticated server fetch helper (no cookies, no auth header)
  calling the public GET endpoint.
- **Rendering**: no collaborative editor, no Yjs/socket session — out of
  scope for an anonymous visitor. The page calls `renderDocumentHtml()`
  from `@notted/shared-validators` (the same defensive JSON→HTML converter
  already used by the HTML/PDF export path, already covered by export
  tests) directly, since both `apps/web` and `apps/api` may depend on
  shared packages per ADR 0001. Output is wrapped with the shared
  `printStylesheet()` for paper-like styling. No new sanitization code.
- `ShareModal.tsx` gains a "Public link" section next to the existing
  "Internal link" section: shows on/off state (`enabled`/`createdAt` from
  the status GET), a "Create link" / "Regenerate link" button that reveals
  the URL once with a copy button, and a "Revoke" button when enabled.
  Gated on `note.capabilities.canShare` — the same flag that already gates
  the rest of the modal's mutating controls.
- Public links always resolve against `NEXT_PUBLIC_APP_URL`, never a
  workspace's verified custom domain (Part 73) — consistent with
  `WorkspaceSwitcher`'s existing `canSwitch` guard, which already refuses
  to let a custom-domain host vouch for cross-tenant routing. `/p/:token`
  therefore needs no tenant-routing awareness at all.

## Error handling

- Public GET: 404 for missing/invalid/revoked/trashed-note tokens — one
  response shape for all of them, so a visitor (or attacker) cannot
  distinguish "never existed" from "revoked" from "trashed."
- Management PUT/DELETE: standard `ApiHttpException` envelope, same as
  `NoteSharesService` (`notFound()` on missing note, standard 403 from the
  authorization guard on an unauthorized actor).
- Malformed token (wrong length/charset) short-circuits to 404 before any
  DB query — same defensive posture `note.schema.ts` request validation
  already uses elsewhere.

## Testing

- Service unit tests: create, regenerate (old token stops working),
  revoke, revoke-when-none-exists (no-op), cross-workspace token isolation,
  trash → 404 → restore → works again.
- Controller auth tests: an actor without `note.update` on the note is
  rejected on all three management routes.
- Public-endpoint tests: valid token, revoked token, trashed note, garbage
  token, token for a note whose workspace was deleted.
- Playwright journey: create link → open in a fresh unauthenticated
  browser context → see read-only content → revoke → 404s.
- Accessibility pass on the new public page (semantic heading, no
  keyboard traps, meets the project's WCAG 2.2 AA bar).

## Explicitly deferred

Password protection, expiry, a workspace-level disable-all-public-links
policy, multi-link history, and view analytics are all real, reasonable
asks — deferred because none were in the approved v1 scope. Each is
additive to this schema (extra nullable columns, no breaking change) and
can follow as its own scoped increment.
