# ADR 0008: Runtime and package compatibility baseline

- **Status:** Accepted
- **Date:** 2026-07-22
- **Last revised:** 2026-08-16 — Part 64 pinned `docx` and `fflate` for Markdown/DOCX/ZIP export and recorded the first *new* copyleft-sweep hit since 2026-08-07 (`jszip`, transitive through `docx`, dual-licensed, MIT elected). Previous revisions are retained in repository history.
- **Related plan parts:** 1–7, 21, 33–38, 40, 41, 44, 61, 63, 64

## Context

`Notted.md` names technology major lines, sometimes as `latest`, but reproducible development needs a supported runtime and a compatibility-tested package set. Some current upstream major releases exceed the brief's selected lines; silently upgrading them would change scope.

## Decision

The evaluated baseline is Node.js `22.23.1` and pnpm `10.34.5`. Node `22.12.0` is the minimum supported runtime and Node 23 or newer is outside this baseline. Part 2 will pin the evaluated versions in the version file and `packageManager`; containers must use those same pins unless that part revalidates and records a newer patch.

### Parts 34–36 editor dependency review

The rich editor added eight further `@tiptap/*` packages, all at the already-evaluated `2.27.1` and all MIT, plus two genuinely new third-party runtime dependencies.

- **Need.** `extension-table`/`-table-row`/`-table-header`/`-table-cell` and `-placeholder` are required by `Notted.md`'s editor feature set; `-mention` and `@tiptap/suggestion` back `@` mentions and the slash menu; `-code-block-lowlight` is what makes code blocks highlightable. `lowlight` and `highlight.js` are the only chain that extension supports, so they are transitive by design rather than a free choice.

### Part 44 generic-attachment dependency review

Generic file attachments added exactly **one** direct runtime dependency — `pdfjs-dist@5.6.205`, in `apps/web` — and nothing in `apps/api`. The matrix row above carries the version reasoning; this section is the four-point review the standard requires.

- **Need.** `Notted.md` §6 requires a preview for supported attachment types. The three alternatives were all rejected on the same ground: `<iframe>`/`<embed>`/`<object>` hand an active format to the browser's own viewer and are ruled out by ADR 0005 (and would not work regardless, because the content endpoint sends `Content-Disposition: attachment`); server-side rasterisation would put a second untrusted-bytes decoder in `apps/api`, the highest-risk dependency class in this codebase, and would cost storage and a job pipeline for a transient view; and shipping no preview at all would leave "download it and open it elsewhere" as the only way to look at a file, which the brief asks to improve on. Rendering to a canvas in the client is the option that adds no server attack surface and no stored bytes.
- **Maintenance.** pdf.js is Mozilla's, is the PDF engine shipped inside Firefox, and releases continuously. `pdfjs-dist` is its published build. The maintenance risk is not abandonment but **churn**: it has changed packaging shape (worker entry, ESM layout, `engines`) more than once in recent majors. That is contained by keeping every reference inside one module, `apps/web/src/lib/notes/pdf-preview.ts`, which declares locally the four calls it uses instead of importing the package's `.d.ts`. A pdf.js upgrade therefore fails at that one boundary rather than anywhere else, and dropping the preview entirely is a one-file change.
- **Licence.** Apache-2.0, verified from the installed manifest in the pnpm store (`node_modules/.pnpm/pdfjs-dist@5.6.205/node_modules/pdfjs-dist/package.json` reports `"license": "Apache-2.0"`, and the package ships its own `LICENSE`). Permissive, compatible with distribution, and **not** a new copyleft obligation — it adds nothing to the `THIRD-PARTY-NOTICES.md` position established for `libheif-js` and `@img/sharp-libvips-linux-x64`. Apache-2.0 carries an attribution requirement that the existing notices file already satisfies in form.
- **Security and cost.** It is a parser for untrusted bytes running **in the reader's browser**, not on the server, so a parser fault is contained by the browser's own sandbox rather than reaching workspace data. It is nevertheless bounded rather than trusted: `isEvalSupported: false` closes pdf.js's optional runtime code-compilation fast path; `disableAutoFetch`, `disableStream`, and `useWorkerFetch: false` stop it issuing any request of its own; `cMapUrl` and `standardFontDataUrl` are deliberately unset so a document referencing an external CMap or font degrades to a substitute glyph rather than reaching for a CDN; the annotation layer is never built, so no embedded action or link can navigate; and `MAX_PDF_PREVIEW_BYTES` (25 MiB) refuses a file large enough to be a memory-exhaustion vector before a single byte is buffered, telling the reader to download it instead. Bundle cost is the main price and is paid only on demand, through the dynamic import. `pnpm audit --prod --audit-level=high` covers it and must stay green.

**Deliberately not added** (each considered and rejected, so a later contributor does not re-litigate it):

- `react-pdf` — a React wrapper around this same `pdfjs-dist`. It would add a second dependency, a second version to keep aligned, and a component API, in exchange for wrapping four calls that are already written out.
- `@radix-ui/react-progress`, `@radix-ui/react-alert-dialog`, `@radix-ui/react-tooltip` — the upload bar, the delete confirmation, and the card's controls are built from the primitives already present (`button`, `dialog`) plus native elements. A single non-interactive bar with `role="progressbar"` and a modal `Dialog` whose destructive action is a plain button meet the same accessible contract without three new packages.
- `lucide-react` inside the attachment node view — already a dependency, but React-only, and the card is a plain-DOM ProseMirror node view. The six icons are hand-authored SVG built with `createElementNS`, so no markup string is ever parsed.
- A file-type sniffer in `apps/web` — the client pre-flight is a *courtesy*; the server re-derives the type from the magic bytes on every upload, so a browser-side sniffer would add a dependency to duplicate a check that is not authoritative anyway.

### Part 64 Markdown/DOCX/ZIP export dependency review

Part 64 added exactly **two** direct runtime dependencies to `apps/api` (`docx`, `fflate`) and **zero** to `apps/web`. Markdown needed none at all. The matrix rows above carry the version reasoning; this section is the four-point review the standard requires.

- **Need.** `Notted.md` §14/row 34 names Markdown, TXT, DOCX and ZIP export. TXT shipped in Part 62 and Markdown is a hand-written walker over the typed `NoteDocument` (no dependency — see the rejection of `turndown` below), so only the two binary container formats needed code this project should not write: OOXML and the ZIP container.
- **Maintenance.** `docx` is the actively released JS OOXML writer (regular releases, single maintainer with a long history); `fflate` is a widely depended-on, deliberately feature-frozen compression library whose zero-dependency surface is its selling point. Neither is deprecated (`npm view <pkg> deprecated` empty for both, 2026-08-16).
- **Licence.** Both MIT, read from the installed manifests in `node_modules/`. **This is the first part since 2026-08-07 to change the copyleft sweep's output:** it returns a fifth hit, `jszip@3.10.1` (`(MIT OR GPL-3.0-or-later)`), pulled transitively by `docx`. The expression is a disjunction, so MIT is elected and no copyleft obligation attaches; the triage is recorded in [`THIRD-PARTY-NOTICES.md`](../../THIRD-PARTY-NOTICES.md), which this part updated. The four pre-existing hits are unchanged.
- **Security and cost.** Both packages decode or emit bytes derived from workspace-authored content, which puts them in the untrusted-input class — but on the **write** side, which is the safer half: neither parses an attacker-supplied archive or document in production. `fflate` compresses buffers the API assembled itself; `docx` serializes a tree the converter built from an already-validated `NoteDocument`. The genuine resource risk is unbounded output, not malicious input, and it is bounded explicitly by `renderZipArchive`'s entry/total/per-attachment caps and by `EXPORT_MAX_ARTIFACT_BYTES`. **Deliberately not added:**

- `turndown` — the obvious Markdown converter, rejected. It converts *HTML* to Markdown, so using it would mean rendering `NoteDocument` → HTML → parsing that HTML back into a DOM → Markdown. That requires a DOM implementation in the API (`jsdom` or equivalent, a large dependency this workspace does not otherwise need) and, worse, it discards the typed structure that is the only reason the conversion can be faithful: task-list checked state, explicit page breaks, code-block language, and mention **identity** (the stable user id, not just the display snapshot) all survive a walk over the typed document and all degrade to guesswork after an HTML round trip. The hand-written walker is more code than an import line and strictly more correct.
- `jszip` — rejected as a **direct** dependency in favour of `fflate`: dual `(MIT OR GPL-3.0-or-later)`, which the repository's copyleft sweep flags and which would have required a licence election on a package Notted calls directly. It arrives transitively through `docx` regardless; that is a materially different position (an implementation detail of an MIT package) and is triaged in `THIRD-PARTY-NOTICES.md`.
- `archiver` — rejected: roughly ten transitive packages, bought to obtain a streaming archive API that cannot be used here, because `ObjectStorageService.putObject` takes a `Buffer`. Paying a dependency cost for an interface the storage port cannot accept is the definition of a bad trade.
- `mammoth` / `officegen` — not evaluated in depth; `mammoth` reads DOCX rather than writing it, and `officegen` is substantially less maintained than `docx` for the same job.

## Alternatives considered

- Use every current latest package: rejected because TipTap 3 and NestJS newer than 10 would silently override the product brief; Drizzle is upgraded only to the minimum stable line required by the selected stable Better Auth adapter.
- Use Node 20: rejected in favor of the currently evaluated Node 22 LTS operational baseline, which provides one runtime for the web, API, auth tooling, workers, and containers.
- Retain Drizzle ORM `0.30.10` by downgrading Better Auth: rejected because no stable Better Auth release was found with verified support for Drizzle ORM `0.30.x`; historical releases were developed against at least Drizzle ORM `0.33.0`, and downgrading authentication to obsolete releases would conflict with `Notted.md`'s `latest` selection and the project's security posture.
- Adopt Better Auth 1.7 prereleases: rejected because authentication is security-sensitive and stable 1.6.24 satisfies the required integration with Drizzle ORM `0.45.2`.

## Consequences

Part 2 records the evaluated runtime/package-manager pins. Part 12 must validate generated PostgreSQL migrations and schema APIs against Drizzle ORM `0.45.2`; Parts 13 and 21 must generate and test Better Auth tables using the installed `1.6.24` adapter. Do not use peer overrides or downgrade Better Auth to conceal incompatibility. Each package-owning part records these exact dependency pins and executable verification, or documents a revalidated patch update. Dependabot or manual updates stay within selected lines unless an ADR approves a major-line change.

There is no package graph yet. Runtime or major-line changes require synchronized container updates and an ADR; rolling back restores the lockfile and runtime pins together.
